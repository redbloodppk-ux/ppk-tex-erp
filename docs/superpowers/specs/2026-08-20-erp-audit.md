## A. Confirmed defects and dead weight

### A1. The `fabric_quality_*` link tables are empty but still queried — HIGH

| Table | Rows | Files still querying it |
|---|---|---|
| `fabric_quality_ends` | **0** | 2 |
| `fabric_quality_warp_count` | **0** | 4 |
| `fabric_quality_weft` | **0** | 4 |
| `fabric_quality_weaving_rate` | **0** | 1 |

A normalised schema layer was built for fabric-quality specs, then abandoned in favour of the `calc_snapshot` JSON column. The tables were never dropped and the code still queries them first, falling back to `calc_snapshot` every single time.

Two costs:

1. **Dead complexity in hot paths.** `stock-measure.ts`, `stock-reductions.ts` and the warehouse pivot all carry "try the link table, else fall back" branches. That is roughly a third of the resolution logic in files that already caused today's warp bug.
2. **A live trap.** If anyone ever inserts a single row into one of these tables, the fallback stops firing for that quality and stock maths silently changes. Nothing warns you.

**Recommendation:** pick one. Either drop the four tables and delete the fallback branches, or populate them properly and delete the JSON path. Half-and-half is the worst of both. Dropping is far less work and matches how the system actually behaves today.

### A2. Fully dead tables — MEDIUM

Zero rows *and* zero code references:

`yarn_purchase`, `yarn_purchase_line`, `resale_lot`, `jobwork_order`, `notification`

`yarn_purchase` / `yarn_purchase_line` is a second, unused model for something `yarn_lot` already does — a duplicate concept that never got removed.

`notification` deserves note: it has 0 rows, yet the bell in your header shows a count. Notifications were re-implemented as *derived* (`lib/notifications/source.ts`) and the table was left behind. `notification_clear` (1 row) is still used for dismissals, so this one is half-migrated rather than fully dead.

12 of your 87 tables are empty; 22 more hold 5 rows or fewer.

### A3. `party` and `customer` are two tables for one thing, joined by NAME — HIGH

- `party`: 192 rows
- `customer`: 167 rows
- 0 customers lack a matching party; 25 parties have no customer row

They are linked **by name text**, not by foreign key:

- `v_customer_outstanding` joins `customer c ON c.name = p.name`
- `unpaid-bills-picker` and the party statement match invoices with `.ilike('party_name', partyName)`
- `invoice` carries **both** `customer_id` *and* a `party_name` text column

It works today only because all 192 party names happen to be unique. The failure mode is quiet: rename a party and its invoice history stops matching — no error, no warning, balances simply change. 9 of 94 invoices already have a null `customer_id` (the jobwork ones), so the two identity paths are already diverging.

This is the same class of problem as today's job-work direction bug: one concept, two representations, kept in sync by convention rather than by the database.

**Recommendation:** make `invoice.party_id` a real FK and treat `customer` as a *role* of a party rather than a separate entity. That is a substantial change — but it is the single biggest structural risk in the system.

### A4. Three live party master screens — MEDIUM

`/app/parties` (266 lines), `/app/customers` (177), `/app/jobwork-parties` (156) are all live, over three tables. Only `/app/parties` is in the sidebar, which suggests consolidation was started and not finished. Same root cause as A3.

## B. Structural risks

### B1. Duplicated implementations of the same logic — HIGH

Found while fixing the bill picker today: the Payments page has its **own copy** of the unpaid-bills list (`payments/page.tsx:1096`), separate from the shared `unpaid-bills-picker.tsx` component. Both do the same job. Only one got the direction bug fixed at first.

This is the recurring theme of every bug found today:

| Bug | Cause |
|---|---|
| Warp double-count | Same pool derived in 3 places; only 1 was fixed in July |
| Job work shown as payable | Direction hardcoded per screen; payment tab fixed, dashboard missed |
| Bill picker showing payables | Two copies of the bill list |

The fix that stops the *class* of bug — a single source of truth per concept — is what `lib/party-streams.ts` now does for direction. The same treatment is worth applying to bill loading.

### B2. Very large files — MEDIUM

| File | Lines |
|---|---|
| `jobwork/page.tsx` | 3,852 |
| `warehouse/page.tsx` | 3,569 |
| `payments/page.tsx` | 2,557 |
| `delivery-challan/dc-form.tsx` | 2,434 |
| `invoices/new/page.tsx` | 2,338 |

These are the files where today's bugs lived. At this size nobody — human or AI — holds the whole file in mind, which is exactly how two copies of the same list end up in one codebase. Splitting the top three by responsibility would pay for itself.

### B3. The ledger layer is scaffolding, not accounting — MEDIUM

210 ledger masters exist. **0 of 94 invoices** and **0 of 154 payments** carry a `ledger_id`. Only the bank side of a payment (`mode_ledger_id`) is populated.

You now have Ledger Groups, Ledger Types, a Ledgers master, opening balances and a Ledger View — a full Tally-shaped chart of accounts that nothing posts to. Today's migrations 256/257 corrected its classification, but it remains ornamental.

**Decide deliberately:** either wire it up (real double-entry, a genuine trial balance) or stop investing in it. The in-between state costs maintenance and misleads — it looks like accounting without being accounting.

## D. What I'd actually do, in order

1. **Drop the four empty `fabric_quality_*` tables and their fallback code.** Highest risk-to-effort ratio: removes a live trap from your stock maths, and it's mostly deletion. *(~half a day)*
2. **Extract bill loading into one shared module**, the way `party-streams.ts` did for direction. Kills the duplication behind three of today's bugs. *(~1 day)*
3. **Decide on the ledger layer** — wire it or shelve it. No code needed to decide, but it unblocks everything else. *(a conversation)*
4. **Drop the 5 fully-dead tables.** Pure cleanup. *(~1 hour)*
5. **Fix `general_purchase` to store per-line GST properly**, so the entry form stops writing blended rates. *(~half a day)*
6. **Plan the `party`/`customer` unification.** Biggest structural win, biggest effort — worth scoping before it bites. *(needs its own spec)*
7. **Split the three largest files.** Ongoing, do it as you touch them rather than as a project.
